# World Wide Web proposal: start with the organization’s information problem

**HG-17 · 1989 · communications computing · concept baseline**

A concept becomes credible when it explains the users, existing assets, adoption constraints, and deliberate scope boundaries.

All `HG-` identifiers are new teaching identifiers. Historical facts below
are attributed to sources; the boundary, decisions, artifact, questions, and
transfer exercise are newly authored. No local historical simulation was performed.

## Source-grounded facts

- **HG-17-F1:** The proposal addresses information loss and relationships across a changing organization, then calls for heterogeneous access, decentralization, and links to existing data. [HG-17-S1](https://www.w3.org/History/1989/proposal.html); Losing Information at CERN; CERN Requirements.
- **HG-17-F2:** It treats sophisticated authorization and accounting as outside the proposed local scope while discussing use of existing protection for protected data. [HG-17-S1](https://www.w3.org/History/1989/proposal.html); Non requirements.

## Retrospective systems analysis

**Boundary.** Researchers, institutional memory, existing databases, diverse computers, links, and local adoption form the proposed information system.

**Interfaces to examine**

- Existing repository → new access layer: adoption depends on useful information being available early.
- Local collaboration → broader deployment: a changed trust environment can invalidate deliberate scope exclusions.

**Decision.** How should a team assess a promising early concept?

- Score it by the eventual market’s feature list.
- Evaluate problem fit, adoption path, alternatives, and the assumptions that must hold in its initial context.

**Teaching recommendation.** Keep the initial scope coherent while recording conditions that trigger redesign.

**Uncertainty.** The later success of the Web does not prove each early design choice was inevitable or universally appropriate.

## HG-17-A1: Concept and scope decision note

This proposed artifact is a compact starting point for review. Its evidence
requests are unexecuted; its rows are not recovered project requirements.

| Item | Proposed disposition | Evidence to seek |
| --- | --- | --- |
| Stakeholder problem | Preserve relationships across people, projects, and repositories | Observed retrieval and handover difficulties |
| Adoption path | Expose useful existing material before requiring migration | Pilot access to representative repositories |
| Boundary change | Reopen protection and governance when access expands | New users, threats, obligations, and ownership |

## Practice engineering judgment

1. Why is access to existing information an architectural requirement rather than only a convenience?
2. When is a non-requirement responsible scoping, and when does it become a dangerous inherited assumption?
3. Pitch a small pilot without using eventual success as evidence available in 1989.

**Reasoning signals for a formative review**

- Frames the problem in organizational work rather than a technology label.
- Recognizes adoption and compatibility as system constraints.
- Keeps historical context distinct from present-day security needs.

**Transfer exercise.** Synthetic: propose a shared engineering knowledge service for three teams using incompatible repositories. Include one deliberate exclusion and its reopening trigger.

**Limits.** This is analysis of the original proposal, not a claim about all subsequent Web standards or a current security recommendation.
