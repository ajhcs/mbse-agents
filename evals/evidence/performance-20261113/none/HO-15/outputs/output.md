The supplied RFC 793 (1981), section 2.6 fact supports a transport claim: receiving TCP has taken responsibility for the data. It does not establish delivery to an end user. Logging a transport ACK as “operator saw and accepted shutdown” skips several distinct claims. An unattended dashboard during shift change makes that gap concrete. The packet supplies the historical source fact; no independent source retrieval or system test was performed here.

| Claim | Minimum evidence it would need |
| --- | --- |
| Transport receipt | The transport acknowledgment, bound to the relevant communication. It supports only the supplied transport meaning. |
| Application receipt | The receiving application validates and records the specific instruction, its identity and target. Transport receipt alone does not establish this. |
| Display | The application records presenting the correct instruction and version to a particular session. Rendering does not prove anyone looked at it. |
| Human acknowledgment or acceptance | A deliberate response from an identified person, bound to the instruction and version, distinguishing acceptance from rejection or deferral. This is an attributable attestation, not independent proof of comprehension. |
| Authority | Confirmation that the issuer and responding actor have the required authority for that target and action, under the current duty assignment. Presence at the dashboard does not confer authority. |
| Performed action | Feedback or observation establishing the required shutdown state of the intended equipment. An accepted instruction or issued command does not establish completion. |

A minimal proposed contract would give each instruction a unique identifier, version, target, requested end state, issuer, designated responsible role, validity period and response deadline. Set those deadlines and the fallback policy from operational needs; none is supplied. Record application receipt, presentation, deliberate human response, authorization, action request and confirmed outcome as separate events with attributable actors and correlated times. A rejection or deferral remains explicit and leaves the work unresolved. Acceptance must not silently act as an execution command unless that behavior has been expressly designed and authorized.

Keep each pending instruction assigned to a responsible on-duty role. A shift handover must transfer the pending instruction and obtain explicit acceptance of responsibility by the incoming operator; a reconnect or a new session must not clear it or count as acceptance. If acknowledgment, ownership transfer or completion is missing by the agreed deadline, retain an unresolved state and escalate through an agreed staffed route. Do not mark success or invent an automatic shutdown policy. Enforce the applicable authorization and equipment interlocks when requesting action. Identify duplicates so retransmission cannot repeat an action, and reject expired or superseded instructions unless deliberately reissued with current authority.

A useful verification scenario starts with an instruction sent just before shift change. Arrange transport ACK and application receipt while the dashboard is unattended. Verify that the log records only the events actually observed, retains a pending human response, and triggers the agreed escalation when its deadline passes. Transfer duty and confirm the incoming authorized operator sees the pending instruction and must respond explicitly. Verify that an unauthorized response cannot authorize action. Following an authorized response and action request, withhold equipment-state confirmation: the system must remain “completion unconfirmed.” Then supply correlated confirmation of the required state and check that completion is recorded separately. Replay a duplicate and an expired instruction and verify no additional or stale action occurs. Capture event logs, identities, handover records and equipment observations against predefined expected states. This is a proposed scenario; it has not been executed.
