Testing every user control independently does not establish complete interface behavior. It can miss dependence on earlier edits, queued commands, timing, operating mode and recovery state. The appropriate next claim is a bounded, stated sequence/state coverage claim supported by independent output observations.

The historical input is only the supplied fact from Leveson and Turner's 1993 Therac-25 investigation: particular editing sequences and timing exposed dangerous state interactions. No further incident detail is inferred, and the historical paper was not retrieved. That observation motivates interaction tests; it does not demonstrate that this teaching prototype has the same mechanism or justify transferring a medical-device class. The prototype has no patient use.

The following is a proposed finite test design, not executed results. Obtain the actual interface/state description, allowable settings, timing/acknowledgement rules and output definition first. Generic placeholders below are **P** (an output-affecting parameter), **M** (a mode), and states **Editing**, **Ready**, **Running**, **Stopped** and **Fault/Recovery**. These are proposed test abstractions, not asserted device features. Map them to real states/controls; mark an absent feature not applicable with a reason. Freeze build/configuration and use a safe surrogate load or output inhibition appropriate to the prototype.

Agree these candidate invariants before judging tests: the applied configuration matches the explicitly accepted configuration; edits/cancelled or stale commands cannot silently change an active output; start/stop and recovery have documented semantics; incompatible mixed mode/parameter combinations cannot be applied; and output stays within the agreed laboratory envelope. These are review proposals until the team accepts or replaces them with the real requirements. Define measurement tolerances and time limits from the instrument, not from the Therac history.

| ID | Proposed sequence/state test | Discriminating observation / candidate defect |
| --- | --- | --- |
| SQ-01 | From a fresh initial state, set P1, accept, start, stop. Repeat the same final settings after a different valid prior run. | Compare independently measured output and applied configuration; exposes hidden history dependence for identical final selections. |
| SQ-02 | Edit P1→P2→P1, accept, start; compare with direct P1. Perform once with deliberate pauses and once at the fastest supported input rate. | Final applied setting and physical output should agree with the accepted P1; tests stale intermediate state and lost updates. |
| SQ-03 | Start from M1/P1; change mode then parameter, and in a paired run change parameter then mode, reaching the same permitted M2/P2. Accept/start. | Compare the two runs and mode/parameter consistency; tests order-sensitive partial updates. |
| SQ-04 | Change P1→P2 then cancel; navigate away/back, start using the accepted configuration. Pair with change then accept. | Distinguish committed and draft values at the output boundary; tests stale cache or cancelled edits becoming active. |
| SQ-05 | Submit an edit and then Start just before, at and just after the edit-acceptance boundary. | Determine which complete configuration is applied and whether Start is refused/queued as specified. No mixed configuration is accepted merely because the display looks correct. |
| SQ-06 | While Running, attempt an edit or mode change; exercise the documented reject, defer or controlled-change path, then stop/restart. | Observe active output during and after the attempt; tests confusion between next-run settings and active settings. |
| SQ-07 | Rapid Start→Stop→Start; separately repeat/double-submit Start and Stop at their supported boundary timing. | Count physical activations and stop/restart transitions; tests duplicate commands, stale queued actions and non-idempotent handling. |
| SQ-08 | Stop while an edit or start acknowledgement is pending, then wait without a further Start. | Observe the complete output path for unintended late activation or resumption; a UI “Stopped” state is not the sole oracle. |
| SQ-09 | If a defined recoverable fault can be safely simulated, introduce it during Editing/Ready and during Running; acknowledge/clear it. | Observe inhibited output, retained settings and whether a fresh start authorization is required by the agreed recovery behavior. Fault clearance alone must not be assumed to mean restart. |
| SQ-10 | Safely reset/restart at the commit boundary and during Running; inspect saved configuration and queued command state before any new command. | Detect partially persisted settings and stale automatic actuation after reboot. Use a documented reset mechanism and safe load. |
| SQ-11 | If commands cross a separable interface, delay an acknowledgement and replay an older command after a newer stop or configuration change, using an approved test harness. | Correlate command/version identity with physical output; tests stale-message rejection and ordering. If no such interface exists, record non-applicability. |
| SQ-12 | Enter a defined invalid/boundary setting after a valid run, attempt acceptance/start, correct it to a valid setting, then start. Include specified minimum/maximum valid values. | Verify invalid input handling and recovery without a hybrid of old/new settings; compare output against the valid final setting and declared limits. |

This is twelve test families with a finite execution schedule. Use two concrete valid configurations and the defined invalid/boundary values; execute each listed pair/branch. For SQ-05, SQ-07 and SQ-10, schedule exactly three offsets around the relevant measured transition (−Δ, 0, +Δ), where Δ and timing jitter are documented from the test harness. The “at” case is a measured interval with uncertainty, not a claim of perfect simultaneity. Publish the expanded case list and fixed repeat count before execution. These selections target distinguishable failure mechanisms; they do not claim every sequence or schedule is covered.

Observe output with a calibrated external sensor appropriate to what the instrument actually produces—for example, voltage/current into a safe load or a position/force/flow measurement if that is the output. Record measurement range, sampling bandwidth, latency, uncertainty and calibration. Independently capture relevant actuator/interface signals and a timestamped user-action trace. Application logs and display capture help reconstruct state but cannot be their own sole success oracle. A separate observer or acquisition path should use the accepted settings/test specification, rather than simply echoing values computed by the same code under test; assess shared clocks, sensors and processing that could conceal a common error.

For each execution retain test ID, state/configuration, exact ordered actions and measured timing, expected result, physical output trace, UI/log trace, discrepancies, and pass/fail/inconclusive disposition. Compare paired runs against predefined tolerances and maximum transient/latency limits. Where the expected behavior is undecided, mark the case blocked on that requirement rather than counting it as a pass. Stop the laboratory run at agreed safe bounds and preserve anomalous traces before changing the software.

Residual limits include longer histories, untested timing windows, scheduler variability, hidden states, unmodeled faults, physical conditions and biases in the measurement chain. After the finite suite, use observed counterexamples and a reviewed transition model to select further stress, concurrency or state exploration. A clean result would support only these scenarios, configurations and observation limits; it would not prove a complete interface, general safety or clinical suitability.
