Engineering skills for reviewable system decisions

MBSE Agents turns system questions into usable concepts, scenarios, requirements, architectures, risk analyses, and verification/evidence plans. Its skills preserve domain analysis and review questions while giving GPT-6.1 Sol and GPT-6 Astra room to work. No persona claims, prescribed document size, or future-model promises.

The collection contains 13 skills: seven engineering tasks, five domains, and one founder review. The generated catalog is the inventory. This is an instruction/resource library with offline maintenance tools; it is not a running agent service or an MBSE modeling engine. Model quality has not been comparatively evaluated for this release.

Start with a task

Requires Python 3.10+ for the optional installer/checks; no packages or credentials. Clone the repository, then either launch Codex here (the .agents/skills folders are discoverable) or install selected packages into your own project:

git clone https://github.com/ajhcs/mbse-agents.git
cd mbse-agents
python scripts/install.py --list
python scripts/install.py --project /path/to/project --skill mbse-requirements --skill mbse-architecture --dry-run
python scripts/install.py --project /path/to/project --skill mbse-requirements --skill mbse-architecture

On Windows, replace /path/to/project with a quoted Windows path; use py if that is your Python launcher. The installer never overwrites AGENTS.md or model settings. Existing unmanaged or edited skills are preserved. Updates to unchanged managed packages require --update and retain backups.

Use $mbse-requirements and $mbse-architecture on our system brief. Develop measurable requirements, function/component allocations, interface contracts, and design rationale. Carry source IDs through the artifacts and identify the missing decisions that could change the design. Save a coherent reviewable draft.

Add a domain skill when domain context matters: mbse-aerospace, mbse-defense, mbse-automotive, mbse-medical-device, or mbse-electronic-systems. For operations, use the concept, ConOps, or scenario skills. For assurance work, use verification/evidence or baseline review. See task workflows.

Choosing and upgrading a model

The skills are authored for GPT-6.1 Sol and GPT-6 Astra, using the same engineering contracts. No comparative model evaluation has been run for this release. OpenAI describes Sol as a balance of speed, cost, and intelligence, and Astra as the choice for demanding reasoning. Use Sol as a practical starting point; consider Astra for difficult cross-domain tradeoffs or unresolved review findings. This routing is a project recommendation to evaluate, not a measured advantage. See the official GPT-6 guide.

config/model-profiles.json records editable model IDs and documentation links. It is informational; installing a skill does not change the host's model setting. Choose a model and supported reasoning setting in your host. For Codex CLI, explicit selection looks like:

codex -m gpt-6.1-sol
codex -m gpt-6-astra

Check the models available to your account and the current CLI documentation. The documented API limitation is that these two models do not support none reasoning effort. This project deliberately has no API runner, credentials, or hardcoded budget defaults.

The Astra skill guidance informs our authoring choices: precise discovery descriptions, task-specific references, fewer repeated instructions, and completion boundaries tied to the requested result. Keep local assumptions and engineering evidence visible while giving the model room to choose methods. Do not require every skill or every reference for every request.

To upgrade:

  1. Fetch official guidance for the exact candidate model and verify availability, tool support, output contracts, and supported settings in the intended host.
  2. Change only the relevant profile and documented invocation. Preserve a baseline revision and record the candidate revision, settings, tools, and sources.
  3. Run the same task cases with baseline and candidate, withholding reviewer rubrics from the producing model. Use the evaluation protocol.
  4. Review failures and total task quality, evidence accuracy, latency, and cost. Update a skill only for observed needs; retain or revert the profile if the candidate does not meet the workload's acceptance conditions.

No promised capability of a future model is part of a skill's contract.

Develop a System Concept

Turn the user's problem into a defensible system direction. Understand whose outcome matters, the current situation, the system boundary, and the decision being made. Explore alternatives that differ meaningfully in how they deliver value, including changes to operations and the option to retain the current approach when relevant.

Connect each candidate's essential functions to stakeholder outcomes and constraints. Examine enabling technologies, interfaces, human roles, lifecycle costs, supply dependencies, and uncertainty at the depth needed for the decision. Test ambitious options against concrete feasibility limits; avoid assuming the first proposed implementation is the system concept.

Deliver the preferred concept, alternatives considered, rationale, assumptions, and the next evidence that could change the choice. Identify infeasible constraints or conflicting outcomes plainly. Continue through a coherent draft and consistency review; ask about missing information that materially affects selection while developing independent parts.

Use concept decisions when a comparison or feasibility plan would help. This skill develops the concept; detailed operating narratives and component designs can follow as the user requests.

Develop a Concept of Operations

Describe how the system will serve its stakeholders in its intended setting. Establish the operational problem, actors, responsibilities, boundary, environment, external systems, and measures of success. Capture normal use and the exceptions that could change the concept: degraded resources, handovers, maintenance, recovery, and retirement as relevant.

Keep operational need separate from a selected implementation. Make interactions and decision authority explicit, including who initiates, supervises, overrides, maintains, and accepts outcomes. Trace assumptions and unresolved stakeholder conflicts to the scenarios or decisions they affect.

Produce a usable ConOps at the user's chosen level of maturity. Connect operational claims to scenario references and evaluation conditions. Review consistency between roles, boundaries, modes, and desired outcomes. Develop what the available facts support and ask targeted questions about consequential gaps.

Use operational framing for a longer ConOps. Do not force a document template onto a focused revision.

Develop Operational Scenarios

Develop the requested scenario or scenario set from a recognizable operational trigger and outcome. Define actors, context, preconditions, system mode, and boundary. Describe actor actions and observable system responses, including exchanged information, material, or energy where relevant.

Explore exceptions that matter to this use case: interrupted work, invalid input, unavailable dependencies, degraded resources, misuse, and recovery. Expose ambiguous authority, hidden timing constraints, and unsafe transitions. Choose scenario coverage based on operational consequence and variation; do not mechanically enumerate every combination.

Deliver coherent normal and exception flows, final conditions, assumptions, and observations that could become requirements or validation cases. Preserve source facts and IDs. Check that an alternative path actually rejoins a defined state or ends with a clear disposition.

Use scenario records for structured handoffs. These records describe operations; do not silently convert every action into a design requirement.

Engineer Requirements

Build a requirement baseline that supports design and verification. Work from stakeholder needs, scenarios, constraints, and existing artifacts. Preserve IDs and agreed wording when possible. Separate source obligations, derived requirements, design choices, and provisional proposals.

Write requirements with a responsible subject, observable behavior or constraint, relevant conditions, and measurable acceptance conditions. Use units, tolerances, timing reference points, and operating envelope where they affect meaning. Flag compound, ambiguous, conflicting, infeasible, or unverifiable requirements and propose repairs tied to their consequence.

Carry source and rationale links into decomposition. Identify derived requirements and feed their implications back to the concept, safety analysis, or stakeholder decision. Do not invent thresholds or standards obligations to make a table look complete.

Deliver the requested baseline or located review findings, with allocations if known, verification intent, and unresolved decisions. Review coverage and consistency before handing off. Use requirement contracts for a structured baseline.

Design a System Architecture

Connect the required behavior to a workable system structure. Use the actual boundary, operating modes, requirements, and constraints. Decompose functions before treating a component list as a complete architecture. Consider alternative allocations or mechanisms when they affect performance, risk, maintainability, or feasibility.

Define interfaces with direction, exchanged item, semantics, units, timing, validity, error handling, and responsibility as relevant. Make resource budgets and dependencies visible. Evaluate shared power, clocks, processors, data, suppliers, and human roles before claiming redundancy or isolation.

Deliver traceable function-to-component and requirement allocations, interface contracts, design decisions with rationale, and unresolved assumptions. Feed newly derived constraints back into requirements and risk analysis. Use the user's modeling tool when available; otherwise provide a clearly labeled textual or diagrammatic proposal without claiming a live model was changed.

Use architecture records for deeper allocation or trade work. Continue until the requested architecture is consistent enough for review, with gaps explicitly located.

Plan Verification and Evidence

Build an evidence plan from requirements, stakeholder needs, risks, and the implemented or proposed configuration. Select test, analysis, inspection, demonstration, or formal analysis based on what can establish each claim. Distinguish verification of requirements from validation of intended use.

Define acceptance conditions, environment, stimuli, observations, uncertainties, and configuration before declaring success. Include relevant normal, boundary, failure, and recovery behavior. Check independence or qualification requirements against the actual program basis and tool use; do not assume a test name or tool output establishes compliance.

Connect each verification activity to the requirements it addresses and the artifact that records its result. Separate planned, executed, failed, reviewed, and accepted states. Missing files, stale configurations, inconclusive results, and unresolved failures remain gaps. Describe the limited scope of simulations and proofs.

Deliver a reviewable plan or evidence assessment and pursue authorized local execution through results and relevant repairs. Do not fabricate execution, certification, or approval. Use evidence contracts when creating a trace or evidence package.

Review an MBSE Baseline

Review the artifacts against the user's actual decision, program basis, and baseline. Follow representative threads from need through requirement, architecture, risk control, verification, and evidence. Inspect uncovered obligations and changed interfaces as well as plausible-looking links.

Prioritize findings by engineering consequence. Locate each finding, explain the mismatch or missing evidence, identify affected IDs and downstream impact, and offer a repair or required decision. Distinguish verified defects from open questions and editorial preferences. Challenge unsupported compliance, independence, test, or proof claims using the sources and artifacts available.

For change reviews, compare the old and new configurations and identify affected requirements, hazards, interfaces, suppliers, verification, and accepted evidence. Reused evidence needs a applicability argument. Do not use the repository's teaching benchmarks as an answer oracle.

Deliver a decision-focused review with findings, evidence examined, coverage limits, and residual gaps. Use review records for larger reviews. Independent review means a fresh assessment with an identified scope; do not claim independence from a self-review.

Defense Founder Review

Evaluate whether the proposed venture can deliver meaningful operational value and become a repeatable product. Start from the actual capability gap and operator, then test the proposed wedge against deployment, procurement, integration, manufacturing, and sustainment constraints.

Examine the whole system, including sensors, compute, software, operators, and support where relevant. Compare build/buy/partner choices by differentiation, interfaces, cost, reversibility, and execution risk. Identify enabling changes with evidence. Investigate incumbent constraints rather than assuming named organizations are incapable or slow.

Shape a prototype plan around the hardest uncertain claim and measurable operator value. Choose milestones that fit resources and the actual setting. Test defensibility through deployed learning, reliability, supply/manufacturing capability, and switching costs; do not treat "AI," relationships, or a pitch deck as proof of a moat.

Deliver a direct, evidence-based recommendation, the system/product thesis, feasible entry point, critical bets, prototype evidence, and conditions that would change or kill the idea. Keep uncertainty visible, respect the user's business objective, and challenge ambition through outcomes rather than forced verdict labels or blanket preference for vertical integration. Stakeholder brief

This fictional project monitors a laboratory cabinet holding temperature-sensitive research reagents. It is not claimed to be a medical device or validated storage system.

Source Need / teaching-project decision
NEED-01 Local warning after temperature has remained at or above 8 deg C for 2 s. This project threshold is not a sourced clinical/reagent limit.
NEED-02 Distinguishable sensor-unavailable indication after 1 s of invalid readings.
NEED-03 High warning remains visible until temperature is below 8 deg C and a technician acknowledges.
NEED-04 Timestamped alarm changes for investigation.

SCN-01: monitor storage, detect a sustained excursion, latch warning, observe recovery, acknowledge, retain event record. SCN-02: invalid/missing readings produce sensor fault; valid reading clears that fault; an existing high warning still needs valid recovery and acknowledgement.

Boundary: sensing interface, alarm logic, local annunciation, event record. Refrigeration control, networks, reagent disposition, and lab quality decisions are outside this demonstration.

Assumptions: samples every 100 ms; monotonic timestamps; power available; a valid reading represents cabinet temperature. Physical accuracy, sound/light perception, power loss, calibration, retention across reset, and staffing/response time require subsequent design and stakeholder validation.

Proposed requirement baseline

Values come from the brief, not regulation. Requirements apply to sampled reference behavior. Timer intervals begin at the first applicable sample, not a physical threshold crossing between samples.

ID Requirement Source Acceptance
REQ-01 The evaluator shall latch high within 100 ms after valid samples have been at or above 8 deg C continuously for 2 s, and not before that interval. NEED-01 First high 2000-2100 ms from first qualifying sample; below-threshold/invalid sample resets pending interval.
REQ-02 The evaluator shall assert sensor fault within 100 ms after readings have been invalid continuously for 1 s; the next valid sample shall clear sensor fault. NEED-02 First fault 1000-1100 ms; clearance on next valid sample. Nonfinite/nonnumeric readings are invalid.
REQ-03 The evaluator shall retain latched high until acknowledgement while the current sample is valid and below 8 deg C. NEED-03 Early acknowledgement, recovery alone, and sensor recovery cannot silently clear high.
REQ-04 The event recorder shall record each change of high/fault state once, with sample time and resulting states. NEED-04 Exact ordered transition records; no event for unchanged state.

Derived interface IFC-01 uses contiguous 100 ms ticks, supporting the model timing claims. Jitter, transport/actuator latency, and persistence need further requirements. No requirement is marked stakeholder approved.

Rendered from examples/worked/cold-storage-alarm/architecture.md

Architecture and allocation

The logical design separates sensing, evaluation, local annunciation, and events. reference_model.py emulates evaluation/event behavior and returns output flags; it does not implement the sensor or sound/light actuator.

Function Requirements Allocation Responsibility
FUN-01 Qualify temperature interval REQ-01 COMP-02 Reset pending timer on invalid/low input; latch after interval
FUN-02 Diagnose input availability REQ-02 COMP-01, COMP-02 Invalid input detection and valid recovery
FUN-03 Retain/acknowledge warning REQ-03 COMP-02, COMP-03 Preserve high latch and expose state
FUN-04 Record state changes REQ-04 COMP-02, COMP-04 Once per changed state pair

IFC-01: (time_ms, temperature_c) on contiguous 100 ms ticks. None, NaN, infinity, booleans, and nonnumeric values are invalid temperatures. The model rejects gaps, duplicate/out-of-order ticks, noninteger times, and nonboolean acknowledgement. IFC-02: acknowledgement at current tick. IFC-03: separate high/fault and their OR as local alarm. IFC-04: ordered time_ms, high, sensor_fault records in volatile memory.

AD-01: high latches, fault automatically clears on valid recovery to distinguish an excursion requiring acknowledgement from a current diagnostic condition. AD-02: discrete ticks make teaching checks reproducible; continuous timing and missing-tick handling remain open. AD-03: transitions are logged once; persistence is open.

HAZ-01: unnoticed excursion, CTL-01: warning plus operator action. HAZ-02: misleading healthy indication during sensor failure, CTL-02: invalid-input detection. Tests check modeled controls; noisy-lab effectiveness and reagent protection are unvalidated. Shared power is a common dependency, not redundancy.
