## Initial findings

### MIR-01 — P2 — Recorded source/input hashes need not identify what executed

Initial locations: `scripts/analyze_gallery.py:190-197` and `:297-300`; `examples/medical-device/smart-infusion-pump/analysis/run_clamp_checks.py:9` and `:61-62`.

The collectors execute previously imported Python objects and then hash current disk files. Importing the clamp runner, changing its model's watchdog threshold from 200 to 300 ms, and invoking the real runner emits 28 passing tests bound to the edited 300 ms source while the trace releases at 200 ms. A fresh uncached replay rejects that record. The same import/edit sequence works for the static analysis engine: old calculations are archived under the edited arithmetic source hash.

The stronger reproduction creates a normal timestamp/size-valid `.pyc`, changes the model from 200 to 300 ms without changing file size or timestamp, and executes with `python3 -B`. Collection exits 0; `--check` exits 0; `gallery.check` returns no errors. The archived source says 300 ms, while the execution observes 200 ms. Removing only the probe-created cache makes the replay fail. `-B` alone does not bind the loaded implementation to source.

There is also an input read-to-hash gap. A deterministic concurrent-edit probe changes the FMS input's BE1 probability from `1/1000` to `1/2` after analysis but before configuration hashing. `run()` returns the old exact result `134173030809261370330999/1000000000000000000000000000000` bound to the new input hash. Fresh evaluation of that new input gives `110023198229038299670001/2000000000000000000000000000`.

Correction: bind loaded modules to their actual source bytes and origin; capture and parse exact input bytes before execution; reject subsequent source/input drift; archive those captured bytes before promoting a current result. Cover stale cache, post-import edit, wrong-origin import, and input changes during collection. This is a defect in the supplied evidence collector, not a request for cryptographic authentication of an arbitrary producer.

Reproduction: `python3 -B .mbse-review/models-independent-probes.py` and `python3 -B .mbse-review/models-input-drift-probe.py`. The latter preserves a single frozen initial fixture and refuses to overwrite it.

### MIR-02 — P2 — Execution receipts can lose their provenance and still pass

Initial locations: `scripts/check_gallery.py:169-180`, `:192-193`, and `:210-211`.

In separate copied examples, reduce either current run's `execution.json` to its `result_sha256` alone. A third probe removes `helper_sources`, `command`, and `executed_at` from the CSE cross-check receipt; it is also accepted without errors. Correct result arithmetic does not establish the missing execution/configuration provenance promised by these records.

Correction: validate required receipt schema, matching run identity and scope, parseable UTC time, nonempty runtime/command, complete source bindings, and result/input identity independently from result reproduction. Historical timestamps need not equal a fresh replay. Preserve earlier run bytes rather than editing old provenance into a new execution.

Reproduction: the three `missing_*_execution_provenance` cases in `models-independent-probes.py`.

### MIR-04 — P2 — Evidence index conflates requirement failures with added proposal violations

Initial location: `examples/medical-device/smart-infusion-pump/assurance-evidence.md:69`.

EVD-MODEL-002 says the temporal study retains “ten retained requirement failures.” The executed record correctly distinguishes ten criterion violations: six failures of the modeled REQ-SAF-001 closure condition and four failures of a separate proposed 500 ms combined watchdog/closure criterion. The latter pass the separately modeled 200 ms release condition; the full REQ-SAF-002 safe-state interpretation remains unresolved. Correction: state ten criterion violations, including six requirement-scope failures and four added proposal violations. Preserve the negative results and the distinction between test-harness success and property/requirement success.

### MIR-05 — P2 — Actuator power loss falsely suppresses processor service events

Initial location: `examples/medical-device/smart-infusion-pump/analysis/clamp_model.py:25-27`; input meaning in `analysis/clamp-study.md:28-30`.

The study defines `power` as the hold-open actuator supply, while `cpu_services` indicates processor watchdog service. Nevertheless, the model records service only when both inputs are true. With `power=False, cpu_services=True`, the trace asserts the watchdog at 200 ms even though actual processor-service events continue. This silently introduces a shared CPU/actuator supply dependency that the stated input contract does not contain.

Correction: either model and document that shared supply explicitly, or honor the actual processor-service input independently of hold-open power. The author chose the latter, preserving the documented input meaning. Power loss already releases the clamp at 100 ms, so this defect affects causal trace interpretation rather than the existing closure-time totals. A regression must check sustained actuator power loss with continuing processor service.
